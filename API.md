# Internal implementation contract

This open-source distribution documents personal (`solo`) installations. The
multiuser, user-password and account-allocation sections below describe retained
compatibility code and tests, not features to enable in a new personal install.
Use `scripts/configure_solo.py` and follow `DEPLOYMENT.md` for a new deployment.

## Personal installation mode

New deployments default to `APP_MODE=solo` through Compose, `.env.example` and the solo installer. The bare backend's `Config.from_env()` retains a `multiuser` fallback for legacy direct invocation; normal Compose deployment explicitly passes the selected mode. The credential database persists its mode; mode mismatch and a preexisting multiuser database refuse startup instead of adopting someone else's records. Solo creates one internal identity only for workspace ownership, never a visible default username or user-provisioning flow. `ADMIN_PASSWORD_HASH` bootstraps the sole site password; later password changes are durable in the credential database. No separate `MANAGEMENT_PASSWORD_HASH` is needed.

Public `GET /api/session` returns `mode:'solo'` in solo mode. `POST /api/login` takes `{password}` only and returns `{authenticated:true,mode:'solo',admin:true,user:{id},csrfToken}`. The one site session authorizes both workspace and `/api/admin/*` settings routes with the same cookie and CSRF, including the fixed official registration/billing browser and Claude authorization WebSockets. Logout and password changes revoke both scopes. Multiuser still requires username and separate administrator sessions.

`POST /api/settings/password` takes `{currentPassword,newPassword,confirmPassword}` with existing Origin/CSRF validation, verifies the old password, saves the new hash atomically and revokes every session. It does not clear files, chat or saved Claude authorization. Solo user administration, per-user quota allocation and workspace lock/password endpoints are disabled; workspace creation cannot enable a password. Workspace files remain isolated from the host and from other workspace containers.

Solo `GET /api/account/usage` returns `quota:null`, official account meters and activity. Station token/percentage allocations and per-user task limits do not gate solo tasks; container resource/running-workspace limits and actual provider limits still apply. Official usage being stale must not manufacture a personal zero balance. Solo `GET /api/status` includes `mode:'solo'` and `claudeAuthenticated`. The frontend uses a password-only login and collapsed same-page settings; `/admin/` redirects to those settings after mode detection. The quota/account-administration contracts below apply to multiuser mode unless stated otherwise.

## Workspace conversation mode

`POST /api/workspaces` accepts `{name, mode}`, where `mode` is `code` or `chat`
and defaults to `code` when omitted. Other values are rejected. Workspace list,
create and state responses include `mode`; existing registry rows migrate to
`code`. The mode is immutable after creation: there is no mode-update endpoint.
To change purpose, create another workspace. This is separate from the site's
`APP_MODE=solo|multiuser` setting.

`GET /api/workspaces/{id}/chat` and chat snapshots include `mode`. Each workspace
keeps its own session and files. Docker resource labels must match the registry
mode; historical unlabeled resources are treated as `code`, never as `chat`.

For `chat`, the Claude command disables tools, MCP servers and slash commands;
the backend also denies all `can_use_tool` requests rather than displaying an
approval button. A conversational system prompt replaces the coding prompt.
It still uses the official Claude Code client and the user's Claude allowance,
not the full claude.ai website product.
Flag semantics are documented in the [official CLI reference](https://code.claude.com/docs/en/cli-reference).

Explicit uploaded attachments are validated in the current workspace and sent
inline. Supported images are PNG/JPEG/GIF/WebP, at most 5 MiB each. Supported
UTF-8 text files are at most 256 KiB each and 512 KiB combined. Each message has
at most 5 attachments and at most 10 MiB of attachment bytes in total. PDF,
Office, ZIP and unsupported binary files are rejected before the turn starts.
The model is not given a file-read tool. Inline bytes are not duplicated into
the application's public chat snapshots or chat database; the official client
may retain them in its own transcript. Other workspace files are not added to
the message by this attachment path.

The protocol and permission boundary are covered by automated tests. Those
tests use mocked client responses; real authenticated CLI text/image turns
must also be verified against the client version installed on the server.

## Account quotas and activity

`GET /api/account/usage` and authenticated/CSRF-protected `POST /api/account/usage/refresh` return `{quota,official,activeTasks,idleMinutes:30}` for the current user only. `quota` contains `mode`, `unit`, `fiveHour` and `weekly`, each `{limit,used,remaining,resetAt}`, plus `exhausted` and `concurrencyLimit:1`. The existing default mode is `tokens`, with unit `tokens`: integer input + output + cache read + cache creation; null limits/remaining mean unlimited and zero limits deny admission. Automatic mode is `official_share`, unit `percent`, with numeric percentage points of a complete account window (20 means 20% of that account window). In percent mode null means unknown, never unlimited; missing allocations return null for all three amounts, while an expired or stale window retains history and sets remaining to null. `blockedReason` explains admission failure. Positive `sharedAdjustment` is a separate shared-account deduction, not personal attributed `used`. `unassignedAccountUsage` is account-wide unmatched usage, not another personal charge. Deleting a workspace never resets use. Deleting the account removes identifying metering records but keeps an anonymous automatic seat for the rest of its current windows, without redistributing that seat's allocation.

`official` contains two `{usedPercent,resetAt,status,updatedAt,stale}` windows and top-level `updatedAt,stale,error`. Missing values are null, not zero; never derive official percentages from local token totals or cost estimates. Read official `get_usage` control responses / usage events only, without model prompts. The client may not supply this information for inference-only setup-token authentication. Refresh is bounded and throttled; stale values remain visibly stale. Manual token mode consumes a known reset exactly once without extrapolating future windows. Automatic mode waits for fresh official confirmation of the next window before allocating its actual remaining pool. Unknown, stale, expired or exhausted account data blocks automatic admission and pauses active tasks. Workspace containers may still start for file access; active official refresh now uses the independent administrator collector.

`GET /api/admin/quotas` returns `{users:[{id,username,deleting,quota}],official,settings:{mode,userIds,accountGeneration}}`. `PUT /api/admin/users/{id}/quota` accepts required `{fiveHourLimit:null|int,weeklyLimit:null|int}`. `POST /api/admin/quotas/distribute` accepts `{fiveHourTotal:null|int,weeklyTotal:null|int,confirmation:"DISTRIBUTE_QUOTA"}`. Limits are bounded to 10^12 raw tokens, integers only. Both mutations require admin authentication, exact Origin and CSRF; return the same admin view. Both return 409 while automatic mode is enabled. Manual distribution includes nondeleting users sorted by ID, integer remainders to the first IDs, preserves all use, and immediately pauses newly exhausted active tasks. UI previews before confirming.

`PUT /api/admin/quotas/automatic` requires admin authentication, Origin and CSRF, and accepts `{enabled:boolean,userIds:string[],confirmation:"CHANGE_AUTOMATIC_QUOTA"}` with no extra fields. Booleans are strict, IDs are unique 32-character lowercase hex account IDs (maximum 1000); enabling requires at least one existing nondeleting user. Changes return 409 while any task is active or awaiting permission, or a container stop remains unconfirmed. On disable the UI sends `userIds:[]`; the server preserves the saved member list and ledger, restoring the original manual limits and usage. Enabling with unknown official data saves the policy but leaves users blocked pending synchronization. Newly created accounts are not automatically members. Nonmembers have zero allocation. Member changes require both original windows to have ended; administrators can disable automatic mode and wait until those deadlines. Responses use the admin quota view above.

Automatic allocation starts each independently confirmed window with `(100 - official usedPercent) / memberCount`. Five selected accounts receive 20 percentage points each only when a complete window starts unused; enabling at 40% account use allocates 12 each for that window. Positive official total changes are apportioned using new durable task token events (input/output/cache have equal weight), with separate pending weights for each window. Duplicate events/reports and same-window mode toggles never issue new allowance. No-weight changes and overflow beyond an attributed user's available balance reduce other available shares proportionately as shared adjustments; total remaining allocation cannot exceed the observed account pool. Values are stored in integer millionths of a percentage point in additional tables in `quota.sqlite3`, sharing the token ledger's transaction lock.

An authorized `get_usage` report with literal `rate_limits_available:true` and an explicit numeric zero plus explicit null reset for the five-hour window confirms an idle cycle. Its normalized official bucket adds `{state:"idle",idleSince:<stable first observation ISO>}`, with `usedPercent:0,resetAt:null`; freshness still expires normally and query errors still block automatic use. Missing windows, missing reset fields, whole-null rows, passive rate events and weekly null resets do not establish idle. A fresh idle cycle can allocate the full pool and admit the first task without inventing a deadline. Personal percentage buckets expose `state:"idle"|"active"|"unknown"` and idle buckets include `idleSince`. The first real active deadline binds the same allocation and pending token weights; first consumption is charged without a second grant. A known unexpired active window cannot be replaced by a zero/null report. The nullable reset schema is migrated transactionally, retaining existing rows and member balances.

An explicit official `rejected` status blocks automatic admission and pauses active tasks even if the last numeric meter is below 100. A newer, complete, explicitly available profile report with numeric usage below 100 and a real future deadline can supersede that old rejection without inventing an `allowed` status. Partial data and passive numeric headers cannot clear it; `critical` severity alone is not an explicit rejection.

This is local allocation accounting, not a provider-issued per-user bill or precise subscription enforcement. Parallel requests, outside-account activity, model/cache weighting and delayed meter reports affect attribution. Early rate-event sources are given up to 30 seconds to supply assistant/result usage before settlement; global exhaustion/freshness enforcement still applies immediately. Already-issued requests can exceed a share before the next observation. Replacing the shared inference authorization invalidates automatic windows and balances while preserving the selected members and manual token ledger; fresh account data is required. UI labels these values as 站内配额 and separately displays 官方账号总额度.

`POST /api/workspaces/{id}/activity` records real interaction with ownership/unlock/CSRF checks, no body. Background GET polling is not activity. Client throttles interactions to once a minute; server maintenance stops idle containers after 30 minutes, never during a task or permission wait. It retains files/history.

`POST /api/admin/quotas/refresh` is the admin-authenticated, Origin/CSRF-protected equivalent of refreshing official meters; returns the admin quota view and rechecks admin session validity after the awaited query.

Official summaries also expose `errorCode:null|'usage_authorization_required'|'usage_authorization_busy'|'no_running_workspace'|'query_timeout'|'query_failed'|'unavailable'|'storage_failed'` and `retryAt:ISO|null`. Codes are fixed safe categories, never upstream exception text. The retry time describes the local 60-second query interval, not subscription recovery or a guaranteed provider retry time. Production actively queries the private administrator profile-authorized CLI, without user workspaces or model prompts. It does not fall back to the inference-only shared token when private authorization is missing. Local successful-ingest revisions prevent a reply already processed by a stream from being relabeled as unavailable. An identical valid timestamp/percentage/reset observation may confirm the cache and clear a query error, but never advances its original measurement time or relaxes the five-minute freshness rule.

## Private administrator usage authorization

`/api/admin/usage-auth` reuses the administrator-only `/status`, `/terminal`, `/terminal/stop`, `/login-browser`, `/login-browser/stop`, and `/login-browser/display` transports. All mutations require administrator session, exact Origin and CSRF; WebSockets require the administrator cookie, matching Origin and initial CSRF frame. Regular users cannot read status, identity or terminal/browser output. A shared lifecycle lock prevents the two administrator authorization flows from running two server browsers concurrently.

`POST /api/admin/usage-auth/prepare` accepts only `{confirmation:"AUTHORIZE_USAGE_FOR_SHARED_ACCOUNT"}`. It invalidates the previous query binding before a new login can replace the private credentials. `claude auth login --claudeai` runs in a private `admin-usage-auth` environment with a separate persistent home and no shared auth mount. After successful CLI exit and profile-scope credential validation, status reports `pendingConfirmation:true` and a bounded `accountEmail` for administrators only. The old inference token lacks trustworthy account identity metadata: the server cannot automatically prove both grants belong to the same account.

`POST /api/admin/usage-auth/confirm` accepts only `{confirmation:"CONFIRM_SAME_CLAUDE_ACCOUNT"}` and requires the same administrator session that completed the current login. This is the administrator's explicit same-account confirmation, not automated identity verification. Successful binding stores the current `OfficialShares.accountGeneration` and administrator-visible email in `app_data/usage_auth.sqlite3`. Status `authenticated` means this saved association matches the current generation, not that a provider request has just succeeded. Credential changes/revocation can still make a subsequent query fail. Rotating the shared inference token changes that generation and invalidates the association. Reauthorizing the usage collector alone never clears personal token/share accounting.

The private CLI home stores full OAuth access/refresh credentials; only the official CLI reads and renews them. No full profile credential, file, home mount or refresh token is passed into user workers or project exports. Login and fixed `initialize`/`get_usage` queries serialize, with bounded timeouts and cleanup; the collector stops after queries, retaining its private home. Official cache invalidation preserves historical percentages while marking them stale and rejects earlier in-flight replies. Backups must include `usage_auth.sqlite3` and the private `admin-usage-auth` home volume. Deleting ordinary workspaces/users does not delete this independent administrator authorization.

Chat snapshots add `{quotaPaused,canResume,quota}` and phase `paused_quota`. Pause state persists in `chat.sqlite3`; quota metering is replay-safe in `quota.sqlite3`. Admission is serialized by the shared lifecycle lock across all workspaces: one active task per user. On a quota event, persist pause then stop the container including children. Failed container stops block new tasks for that user and are retried. Already issued model requests can exceed a local limit before their usage is reported.

`POST /api/workspaces/{id}/chat/resume` requires the owning unlocked session, remaining quota, available task slot and allowed model. It starts the stopped workspace automatically and sends a continuation to the saved Claude session, checking completed operations rather than replaying the original task. It is not an OS process checkpoint. Unknown legacy sessions baseline cumulative result usage instead of charging historical work as current use. Per-message usage is still charged when present.

User UI keeps quotas in the account menu, running/paused state in the transcript, and a device-local permission sound toggle. Deduplicate sounds by workspace/session epoch/request ID; never approve on the user's behalf.

Python FastAPI backend serves built static frontend at `/`. API responses are JSON except the workspace archive download, which returns ZIP bytes; errors before streaming are `{detail: string}`. Same-origin session cookie, HttpOnly, SameSite=Strict. Mutating HTTP calls must send `X-CSRF-Token` from session. Browser uses relative URLs only. `/api/health` public; all workspace endpoints authenticated. Never accept host filesystem paths or command strings.

* GET `/api/session` => `{authenticated: boolean, user?: {id,username}, csrfToken?: string}`
* POST `/api/login` `{username,password}` => `{authenticated: true,user:{id,username},csrfToken}`; username/password identify an independent account. Both fields are required; missing username must not fall back to `owner`. There is no public registration endpoint. New installations have no default user; the administrator creates each account through `/api/admin/users`.
* POST `/api/logout` => `{ok:true}`
* GET `/api/status` => `{docker: boolean, workerImage: boolean, maxWorkspaces: number, error?: string}`
* GET `/api/workspaces` => `{workspaces: [{id,name,createdAt,running,passwordProtected,locked,...}]}`; only the authenticated user's workspaces. Locked entries omit chat/terminal activity detail.
* POST `/api/workspaces` `{name,password?}` => workspace (201); creates and starts container owned by the authenticated user. Name 1–60 chars, display only; optional password is 8–1024 characters. A protected new workspace starts unlocked in the creating session.
* POST `/api/workspaces/{id}/unlock` `{password}` => workspace; bounded password verification, rate limited. A successful grant belongs to the current user session and current workspace password revision.
* POST `/api/workspaces/{id}/lock` => workspace; drops this session's unlock grant. Frontend immediately clears private drafts, attachments and files; running tasks continue.
* PUT `/api/workspaces/{id}/password` `{currentPassword,newPassword,confirmPassword}` => workspace; require the existing password even if already unlocked. Nonempty new password is 8–1024 characters and must match confirmation; both empty remove protection. Changing protection invalidates all older grants, then grants the current session access. Passwords are hashed, never returned or saved to browser storage.
* POST `/api/workspaces/{id}/start` => workspace
* POST `/api/workspaces/{id}/stop` => workspace; stops Claude and container, keeps files.
* DELETE `/api/workspaces/{id}` => `{ok:true}`; permanently removes this workspace and its volumes, frontend explicit confirmation.
* GET `/api/workspaces/{id}/files?path=` => `{path,entries:[{name,type:'file'|'directory'|'blocked',size}]}`
* GET `/api/workspaces/{id}/file?path=` => `{path,content,encoding:'utf-8'|'base64',size}` (10 MiB limit)
* GET `/api/workspaces/{id}/archive` => `application/zip` attachment containing the entire workspace root; authenticated owner, current unlock grant and a started workspace required. No caller-supplied filesystem path, archive command or exclusion list. See the archive contract below.
* PUT `/api/workspaces/{id}/file` `{path,content,encoding?:'utf-8'|'base64'}` => `{ok:true}`; create/replace file, existing parent required
* POST `/api/workspaces/{id}/directory` `{path}` => `{ok:true}`; create one directory
* DELETE `/api/workspaces/{id}/file?path=` => `{ok:true}`; file or recursive directory, frontend explicit confirmation
* POST `/api/workspaces/{id}/attachments` `{name,content}` => `{path,name,size,mediaType}`; base64 file content, 10 MiB maximum decoded size. Requires the normal authenticated session, Origin and CSRF checks. Stores the file in a server-generated `uploads/<uuid>/<basename>` directory inside this workspace without overwriting another upload. Reject unsafe filenames and paths. Raster media types are derived from bytes; other types use `application/octet-stream`.
* Legacy user `/api/workspaces/{id}/terminal` and `/login-browser` endpoints are unavailable, including their stop/display routes. A user session cannot access the administrator's shared Claude authorization, terminal replay, account identity or browser clipboard. Shared workspace authentication is exclusively under `/api/admin/claude/`; the administrator registration/billing browser below uses an independent temporary profile.

Every workspace route checks account ownership, including files, uploads, chat polling, model selection and permission responses. Unknown IDs and another user's IDs return 404; a protected workspace without a current grant returns 423 before exposing private contents. Lock, unlock and password change authenticate ownership without requiring an existing grant. Logging out or resetting a user's login password invalidates that user's grants. The frontend must clear cached private content on 401/423 or deleted workspaces and must not mount chat or fetch files for a locked workspace. Password protection is application access control, not encryption at rest; trusted server administration still controls the data.

File paths are always relative to `/workspace`, no symlinks, traversal, absolute paths. File operations require started workspace. No generic shell endpoint. The user UI contains Chinese chat, model selection and workspace files; administrator authorization is handled on `/admin/`. No fake status/data outside explicit demo fixtures.

## Administrator Claude registration and billing browser

Only an authenticated administrator may open this ephemeral browser from the "Claude 账号管理" card on `/admin/`. No workspace needs to be created or started. Ordinary dashboard user sessions cannot access the browser; the previous `/api/account/claude-browser` HTTP and display endpoints are unavailable. The browser is separate from shared Claude Code authorization: registering or subscribing does not complete, replace or import that authorization. The administrator must still authorize shared Claude Code separately in its existing section. The browser has no workspace, home, credentials or Docker-socket mounts.

* GET `/api/admin/claude-account-browser` => `{active,browserId,purpose,expiresAt}` for the current administrator login session. Another session occupying the global browser slot returns 409 without its identity or page data.
* POST `/api/admin/claude-account-browser` `{purpose:'register'|'billing'|'usage',browserId?:string}` => current browser metadata. Fixed initial pages are respectively `https://claude.ai/login`, `https://claude.ai/settings/billing` and `https://claude.ai/settings/usage`. No arbitrary URL, host IP, account ID or user ID is accepted. A live browser requires its current `browserId` and navigates within the same temporary profile; navigation does not extend the original 30-minute deadline.
* POST `/api/admin/claude-account-browser/stop` `{browserId}` => `{ok:true}`. Stale IDs cannot close a new lease. Closing removes the ephemeral browser and its dedicated network; previously saved administrator authorization remains untouched.
* WebSocket `/api/admin/claude-account-browser/display` requires the administrator cookie, exact Origin and initial JSON `{type:'auth',csrfToken,browserId}` before binary RFB messages. A different administrator login session cannot attach. One active display connection per lease; revalidate session/lease continuously and before sending or accepting data.

Mutating HTTP requests require administrator authentication and the existing Origin/CSRF checks. Administrator session invalidation or expiry invalidates access; a background watcher cleans the environment even without a display connection. Page reload may reconnect the same unexpired lease. Explicit close, administrator logout, expiry and service shutdown clean up; any failed cleanup must fail closed rather than handing a live profile to another session. Startup reconciles only this installation's fixed, owner-labelled account-browser resources. Administrator account-management and Claude authorization browsers share one global browser resource slot.

The display keeps mouse/touch controls and password-style transient mobile input, with no clipboard capture, page recording, stored passwords, autofill card/address persistence or automated purchase. The administrator types and confirms only on the official remote page. Browser and Claude traffic use the same public-HTTPS egress proxy; local/private targets remain denied. Same egress is not a guarantee of a permanent or exclusive public IP. Subscriptions/credits apply to the official account currently open in that browser; they do not automatically change the site's shared authorization or local quota ledger.

## Workspace ZIP archive

`GET /api/workspaces/{id}/archive` uses the same user session and ownership/lock checks as other workspace reads. Another user's or unknown ID returns 404, missing/expired access returns 401, a protected locked workspace returns 423, and a stopped workspace cannot export. The route returns binary ZIP bytes with `Content-Type: application/zip`, an attachment filename generated by the application, accurate `Content-Length`, and `Cache-Control: no-store`. The caller cannot choose a host path, shell command or arbitrary archive destination.

Run a fixed trusted Python helper in the selected worker as its unprivileged user. Its only root is `/workspace`. Use directory descriptors and `O_NOFOLLOW` for traversal and file reads, including identity checks around concurrent filesystem changes; do not follow directory or file symlinks. Include hidden entries, uploads and empty directories. Symlinks are represented by their link text and UNIX symlink mode without reading their targets. Hardlinks, non-regular special files, cross-device directories and unsafe names (including backslashes, colons, control characters and traversal components) reject the whole archive rather than silently omitting entries. Do not read `/home/claude`, shared authorization, host paths or other workspaces. Files the user placed inside `/workspace` are part of the export; project `.env` files are not automatically redacted. This is a project export, not a full backup or filesystem snapshot.

Bounds: 512 MiB total raw content, 256 MiB resulting ZIP, 50,000 entries, maximum depth 100 and a 16 MiB aggregate path-text budget. The helper and broker enforce the 180-second generation deadline; the worker process must also terminate independently if the Docker client disconnects. An empty workspace produces a valid empty ZIP. Filesystem errors, unsafe entries, exceeded bounds, timeout or nonzero helper exit fail the export before any ZIP response is delivered. Existing workspaces receive the current helper source from the web service, so this feature requires only a web image update.

The broker consumes stdout in bounded 64 KiB chunks into an anonymous `TemporaryFile` under `DATA_DIR` (`app_data`), not the web container's small `/tmp` tmpfs. Only a fully generated, successful archive may be served. One global export slot covers both generation and the entire response transfer; another request receives 429 instead of allocating another archive or waiting indefinitely. Transfer is bounded to 240 seconds. Revalidate session, account ownership and unlock access after awaited generation and before each response chunk. Logout, password reset, workspace locking or deletion must prevent further delivery. Close the temporary file and release the slot on success, cancellation, disconnected clients, authorization failure and all error paths. Already delivered bytes cannot be revoked.

The frontend keeps “下载当前文件” and adds “下载工作区 ZIP”. Use the normal same-origin user session, fetch binary bytes, and create a local download only after the complete response is received and its length verified. Cancel on workspace/account change, lock or logout; ignore late responses from obsolete generations and revoke Blob URLs. Do not save a partial or stale ZIP, or interpret HTTP errors as archives. Keep errors visible, prevent duplicate download clicks, and allow explicit retry. The browser buffers the ZIP, so bounded server streaming does not eliminate client memory requirements.

## Implementation and deployment boundaries

Frontend ownership: `frontend/` only. Vite vanilla JS, @xterm/xterm + fit addon. Build emits `frontend/dist`. Backend ownership: `backend/`, `tests/`. Deploy ownership: `deploy/`, `compose.yaml`, `Dockerfile`, `.env.example`, `.dockerignore`, `.gitignore`, `requirements.txt`, `requirements-dev.txt`, README.md, scripts/.

Deployment contract: web port 8000, env DATA_DIR=/data, PUBLIC_ORIGIN=https://your-domain, ADMIN_PASSWORD_HASH=scrypt hash (format supplied by backend auth), COOKIE_SECURE=true, WORKER_IMAGE=claude-cloud-worker:local, EGRESS_CONTAINER=claude-cloud-egress, WORKSPACE_MEMORY=3g, WORKSPACE_CPUS=1.5, MAX_WORKSPACES=30, MAX_RUNNING_WORKSPACES=5. These retained compatibility defaults target the 24-GB profile; the beginner deployment explicitly selects 8g (1536m memory, 1 CPU, 20 saved and 3 running workspaces). Existing .env settings are not automatically changed by a source upgrade, and counts apply across all accounts. Backend uses Docker CLI + socket; web NEVER mounts workspace volumes. Each worker gets its own internal Docker network + volume `/workspace` + home volume `/home/claude`. Worker user 1000:1000, read-only root, dropped caps/no-new-privileges, tmpfs /tmp, limits. Egress proxy attached to each internal workspace network with alias `egress` by backend; proxy forwards only public HTTPS, blocks private/metadata addresses. Worker HTTPS_PROXY=http://egress:3128. No shared network between workers. Compose egress static name above; web must not share workspace networks. Worker entrypoint is `sleep infinity`; `/usr/local/bin/claude` executable available; a legacy helper `/opt/claude-cloud/file_helper.py` is copied into the image, but file requests execute the current web application's fixed trusted helper source with `python3 -I -c` as UID 1000. User input is only JSON on stdin, never executable source; this keeps existing worker containers compatible after a web-only update. Worker volumes initialized by Docker image directory ownership. Container workdir /workspace. Worker home volume must not contain binary installation; install CLI under /opt and expose in /usr/local/bin. No --dangerously-skip-permissions.

`python3 scripts/configure_multiuser.py --profile 24g` updates only the four resource settings in an existing `.env`. Profiles `8g`, `12g`, `24g` map to memory/CPU/saved/running as `1536m/1/20/3`, `2g/1/20/3`, and `3g/1.5/30/5`; default is `24g`. Smaller servers must explicitly select `8g` or `12g`. Run the profile script only when deliberately changing resource values; replacing source alone does not change those values. The ZIP-download update keeps the existing configuration and does not require running this script again. It preserves unrelated lines and literal password quoting, retains the first private `.env.multiuser-backup`, rejects unsafe links, duplicate managed values and detected concurrent edits, and uses atomic replacement. Stop workspaces before applying the profile and rebuilding web. On their next start, stopped containers with differing memory/CPU settings are recreated with the same verified image, files/home volumes and network; running mismatched containers require a stop first. This does not upgrade the CLI image or change the existing 300-GB disk layout, filesystem, or disk quotas.

## Independent administrator page

`/admin/` serves a separate frontend for shared Claude authorization, user accounts, individual/batch user deletion, all-workspace cleanup and Fable permissions. `/admin` redirects to that page. Admin sign-in uses optional `MANAGEMENT_PASSWORD_HASH`, configured locally with `python3 scripts/configure_admin.py`. An empty setting disables admin sign-in; it never falls back to a dashboard password. The admin password is fixed configuration; no web endpoint changes it.

* GET `/api/admin/session` => `{enabled:boolean,authenticated:boolean,csrfToken?:string}`.
* POST `/api/admin/login` `{password}` => `{authenticated:true,csrfToken}`; exact Origin, login rate limit and bounded password hashing apply.
* POST `/api/admin/logout` => `{ok:true}`; requires admin session, exact Origin and admin CSRF token.
* GET `/api/admin/users` => `{users:[{id,username,deleting,...}]}`; no password hashes. `deleting:true` is durable cleanup-in-progress or incomplete-cleanup state; this account cannot log in or resume workspace access.
* POST `/api/admin/users` `{username,password,confirmPassword}` => `{user}` (201); username is 3–32 lowercase letters, digits, `_` or `-`, and unique. Both password strings must match and be 12–1024 characters, different from the fixed administrator password.
* PUT `/api/admin/users/{id}/password` `{newPassword,confirmPassword}` => `{ok:true,sessionsRevoked:true}`; reset the selected account only. The same password requirements apply; only this user's sessions are revoked.
* POST `/api/admin/users/{id}/delete` `{confirmation:"DELETE_USER_AND_DATA"}` => `{deleted:boolean,userId,username,deletedWorkspaces,failed:[{id,name,error}],remaining}`; requires explicit frontend confirmation of the selected account and data removal. Persist the account's deleting state and revoke its sessions before cleanup. Stop and delete only this user's workspaces, files/home volumes, uploads and chat history; remove the account only once all owned data has been cleared. If cleanup fails, return `deleted:false`, keep the account disabled with `deleting:true`, and retain enough registration information to retry after restart. `remaining` can be `null` when enumeration fails; entries in `failed` can describe account finalization as well as workspace cleanup and must not be counted as failed workspaces. The frontend must not report complete deletion for a partial result. Other accounts, their sessions/data, shared Claude authorization and Fable policy remain intact. `owner` may also be deleted and must never be reseeded automatically on startup.
* POST `/api/admin/users/delete-batch` `{userIds:[...],confirmation:"DELETE_USERS_AND_DATA"}` => `{results:[single-user deletion result],deletedUsers,failedUsers}`; accepts 1–100 unique user IDs and requires explicit frontend confirmation of the selected accounts. Atomically mark all selected accounts deleting and revoke their sessions before beginning cleanup. Process every selected account even if an earlier account fails; successful users are removed, unsuccessful users remain disabled and retryable. Counters count accounts, not workspaces. A result's `remaining` may be `null` if the remaining workspace count could not be established; never treat unknown as zero or as successful deletion. Unselected accounts and shared authorization remain intact.
* PUT `/api/admin/user-password` `{newPassword,confirmPassword}` => same result; legacy compatibility route resets the migrated `owner` account only. New frontend uses the account-specific route.
* GET `/api/admin/workspaces` => `{workspaces:[{id,name,ownerId,username,running,passwordProtected,...}]}`; summary metadata across all accounts, never password hashes or project contents.
* POST `/api/admin/workspaces/delete-all` `{confirmation:"DELETE_ALL_WORKSPACES"}` => `{deleted,failed:[{id,name,error}],remaining}`; explicit frontend confirmation. Stops tasks and deletes all registered workspace containers, files/home volumes, uploads, chat history and unlock grants. Keeps accounts, login passwords, Fable policy and shared Claude authorization. Partial failure is reported and retryable; frontend must not report full success if failures or remaining items exist. Workspace access/creation is blocked during cleanup; a competing cleanup returns 409.

All administrator mutation routes require the independent admin session, exact Origin and admin CSRF token. Extra fields are rejected and errors never reflect passwords. Read routes require an admin session.

Account deletion covers application-managed account and workspace data, not general server logs, previously downloaded copies or external backups. An incomplete account deletion must continue denying login and all user APIs, including login attempts already hashing a password when deletion begins; resetting a password must not reenable a deleting account. Cleanup is serialized with workspace lifecycle operations and other destructive cleanup. Confirmed cleanup continues after client disconnect/cancellation and is awaited during graceful shutdown; interruption of the service leaves the persistent deleting state disabled and retryable by an administrator after restart. Failure to enumerate registered workspaces or finalize account storage returns an incomplete cleanup result when possible, preserving that state; an unexpected failure can still return an error. Refresh the account list before retrying, and never interpret an unknown remaining count or error as full deletion. This feature requires rebuilding web only and retains worker/browser images. The deletion and ZIP-download features do not require a resource change; retain the installation's existing resource profile. A separate resource adjustment uses the profile command documented above.
* GET `/api/admin/model-policy` => `{fableAllowed:boolean,revision:number,enforcementReady:boolean}`; requires admin session.
* PUT `/api/admin/model-policy` `{fableAllowed:boolean}` => same policy response; requires admin session, exact Origin and admin CSRF. Strict boolean only; extra fields rejected. Applies immediately without restarting web. Fable starts disabled and policy persists in `auth.sqlite3` independently of passwords. A 503 can mean revocation was committed but Docker application or task shutdown is incomplete: refresh GET, show the incomplete state and retry PUT with the same value. Do not display success while `enforcementReady` is false.

Disabling Fable blocks new Fable selection and messages before stopping affected workspace containers. It stops active Fable chats, pending switches to Fable, default-model chats whose actual model is not yet known, and all raw terminals (their current model cannot be reliably observed). Known non-Fable Chinese chats continue. Files, login volumes, conversation history and selected model remain intact; users with Fable selected must select another allowed model and start the stopped workspace before continuing. Failed stops are retained for retry. Pending synchronization blocks new chat submissions, model changes and process launches.

The broker writes a managed policy to its owner-labeled `cc-{owner}-model-policy` volume and mounts it read-only at `/etc/claude-code` in every worker. It sets `availableModels`, `enforceAvailableModels` and `deniedModels` so the official CLI's raw `/model` command obeys the same restriction. Claude Code >=2.1.283 is required; the broker refuses to run older versions. A stopped legacy worker without this mount is recreated after checking ownership, its two data volumes, network and original image; it retains that exact image, files and login volumes, and uses current resource limits. The policy volume can be regenerated from `auth.sqlite3`. This governs the application's official CLI, not account-wide entitlements or custom API clients someone writes with their own credentials.

Admin sessions use an independent `claude_cloud_admin_session` cookie, HttpOnly, SameSite=Strict, Secure under HTTPS, path `/api/admin`, lifetime 30 minutes. A dashboard cookie or dashboard CSRF token cannot authorize admin operations; admin credentials/session do not grant direct workspace API access. New passwords and CSRF tokens are never persisted in browser storage.

User accounts and password hashes are stored in `/data/auth.sqlite3` in the existing `app_data` volume. A fresh database persists administrator-created-user mode and starts with zero users; it must not create an account after restart or after all users have been deleted. Existing multi-user databases retain their accounts and legacy mapping. Only migration of a durable original single-password database creates `owner` from its saved dashboard hash and assigns legacy workspaces to that account, preserving files and conversations. Newly generated `ADMIN_PASSWORD_HASH` is an unprinted random compatibility seed, not a default user's login credential; later environment changes never overwrite a web-managed password. Successful changes are committed before revoking that user's sessions. Administrator and other user sessions remain valid; workspace files, Claude login credentials and running tasks are preserved. Login attempts begun before a password change cannot create an old-password session after it. Password changes neither rewrite `.env` nor require restarting web. The multi-user migration changes the database schema: back up all of `app_data` and volumes before starting the new version; rollback requires the matching pre-upgrade database and code, not just an older source archive.

## Direct Chinese chat

The user input is preserved without translation or whitespace trimming. Text is at most 16000 characters and must be nonblank unless attachments are supplied; a single assistant reply is limited to 64000 characters. Plain text messages are forwarded unchanged. For messages with attachments, the backend appends a separate file manifest with absolute `/workspace/` paths and an instruction to read the files as needed; history preserves the original user text and attachment metadata separately. Claude receives an appended instruction to answer in Simplified Chinese by default, honor explicit user language requests, and preserve code, paths, commands and quoted text. The browser displays the original assistant reply directly. Neither chat admission nor message delivery depends on a translator.

Authenticated endpoints use the normal same-origin session and CSRF convention for mutations:
* GET `/api/workspaces/{id}/chat` => chat state below.
* PUT `/api/workspaces/{id}/chat/model` `{model:'default'|'sonnet'|'opus'|'haiku'|'fable'}` => state; changes the model for subsequent messages. An idle live process must acknowledge the `set_model` control request before success is returned and the preference is saved. An inactive session saves the preference without starting Claude. Busy sessions, pending approvals and active raw terminals return 409. Fable returns 403 when administratively disabled; unfinished policy synchronization returns 503. Additional body fields and arbitrary model/command strings are rejected.
* POST `/api/workspaces/{id}/chat/message` `{text,attachments?:[{path,name}]}` => state (202), starts one background turn per workspace. Up to five attachments; each must resolve to an existing regular, single-link file inside this workspace's `uploads/<uuid>/<basename>` and be at most 10 MiB. The backend revalidates paths and obtains authoritative metadata before admitting the message. A message can contain only attachments. Preserve the exact user text including leading/trailing whitespace and newlines. `translatedText` and unsupported extra fields are rejected with 422. Browser disconnection does not stop the running turn.
* POST `/api/workspaces/{id}/chat/permissions/{requestId}` `{allow:boolean}` => state; once-only approval of exact pending tool input. Never accepts modified tool input/commands or persistent allow rules. Pending approvals expire after 5 minutes and are denied.
* POST `/api/workspaces/{id}/chat/stop` => state; ends chat process and recycles the workspace container (other container processes also end), retaining history and files.

The old `/api/translation/status` and workspace routes `/api/workspaces/{id}/chat/preview`, `/api/workspaces/{id}/chat/back-translate` and `/api/workspaces/{id}/chat/messages/{messageId}/translate` return 410 after the normal authentication and mutation checks; they never invoke a translation model. The frontend does not call them or offer a translation retry/review control.

Chat state: `{phase:'idle'|'starting'|'thinking'|'awaiting_permission'|'switching_model'|'error'|'stopped', busy:boolean, active:boolean, error:string|null, selectedModel:string, activeModel:string|null, modelOptions:[{value:string,label:string,disabled:boolean}], fableAllowed:boolean,modelBlocked:boolean,policySyncPending:boolean,policyRevision:number, messages:[{id,role:'user'|'assistant',text:string,original:string,translationStatus:'not_needed'|'pending'|'done'|'failed',sent?:boolean,createdAt:string}],permissions:[{id,tool,input:object,title:string}],revision:number,epoch:string}`. `epoch` is the current ChatSession UUID; compare revision only within the same epoch. New user messages store the exact input in `text`; new assistant messages store the exact reply in `text`. Both use `translationStatus:'not_needed'` and `original:''`. The older status values and `translationReviewed` metadata may remain in preserved history and do not request new translation.

Historical messages keep their existing `text` and `original`. Display the existing text when present; a different original can be expanded as historical original text. When an old message has only `original`, display that original instead of an empty translation placeholder. Do not automatically resubmit old tasks. Render message content through the safe Markdown renderer (headings, lists, tables and code); never execute raw message HTML or load external images. Tool parameters remain escaped raw text. History is bounded and persisted in the existing chat database.

Messages may also include `attachments:[{path,name,size,mediaType}]`; file bytes remain in the workspace volume, not the history database. The composer uploads sequentially, supports file selection/drop/image paste, and blocks submission while an upload is pending or failed. Draft attachments remain scoped to their workspace; logout clears draft state. Removing a draft attachment does not delete the saved file. Only locally selected or authenticated workspace PNG/JPEG/GIF/WebP bytes may be previewed as images; SVG/HTML and remote Markdown images are never rendered as active content. Revoke temporary preview URLs when no longer needed. Other file formats can be uploaded and downloaded; successful interpretation may require tools in the worker.

`selectedModel` defaults to `default` and persists separately for each workspace; existing session IDs and messages survive updates. Launch and resume pass the selected alias using `--model`. Live changes map `default` to JSON `null` in the official `set_model` request. `activeModel` contains only the main Claude session's reported model identifier and is cleared after switching until a fresh report arrives. Fixed choices are not an entitlement check: account restrictions may be reported on the next generation. Rejected changes retain the saved preference; a lost acknowledgement stops the ambiguous process before later resuming with the saved model. Keep Fable visible but disabled when forbidden, preserve drafts on policy updates, and use policy readiness revisions to ignore stale polls.

The user frontend contains chat, model selection and files with no raw terminal, account identity or login browser. The administrator authorizes once on `/admin/`; users start their workspace and send messages. `chat.active` remains true between turns until stopped, and workspace objects include `chatActive`. Poll the current chat approximately every 1.5 seconds while authenticated and visible; preserve drafts on errors and ignore late responses after workspace changes. Model and tool permission guards are unchanged. Missing shared credentials produce a generic request to contact the administrator.

Normal deployment does not build or run translation models. The optional `legacy-translation` Compose profile retains the old `translator` definition only for upgrade cleanup; `web` has no translator dependency, environment URL, or translation network attachment. Upgrades rebuild `web`, then stop the old container with `docker compose --profile legacy-translation stop translator`. No workspace, authorization volume or history deletion is needed.

## Administrator-only Claude authorization

* GET `/api/admin/claude/status` => `{authenticated:boolean,terminalActive:boolean,...}`. `authenticated` means a shared token is locally configured, not that subscription availability was tested with a paid request. No token is returned.
* WS `/api/admin/claude/terminal` uses the independent admin cookie, exact Origin and first frame `{type:'auth',csrfToken}`. Runs only the fixed official `claude setup-token` command in a dedicated login container. Server frames are `ready`, `output`, `exit` and `error`; client frames are `input` and bounded `resize`. Token output is captured privately and excluded from displayed/replayed terminal data. One controlling admin connection at a time.
* POST `/api/admin/claude/terminal/stop` cancels the temporary authorization process. Requires admin session, Origin and CSRF.
* GET `/api/admin/claude/login-browser` => `{active:boolean,expiresAt:string|null}`.
* POST same path `{url}` => same state; requires active admin authorization terminal plus admin cookie/Origin/CSRF. Only initial official HTTPS OAuth URLs are accepted, never arbitrary host/command/path input.
* POST `/api/admin/claude/login-browser/stop` => `{ok:true}`; destroys the owned temporary browser.
* WS `/api/admin/claude/login-browser/display`: admin cookie+exact Origin, first frame `{type:'auth',csrfToken}`, then binary RFB frames. Admin session validity is checked throughout the connection. User cookies cannot authorize any of these routes.

Successful `setup-token` completion saves a single validated long-lived OAuth token to the private owner-labeled `cc-{owner}-shared-auth` volume after stopping ongoing workspace processes. Workers mount it read-only at `/run/claude-cloud-auth`; a fixed wrapper sets `CLAUDE_CODE_OAUTH_TOKEN` inside the process, never in Docker configuration or command arguments. Structured chat combines `--restricted` and `--safe-mode` with explicit `Bash,Read,Write,Edit,Glob,Grep` tools, ignoring user/project settings that could select another credential source. Shared authorization does not share workspace home/history directories. Old per-workspace credentials remain intact but are not the app's authentication source. Revoked/expired credentials require the administrator to authorize again. Runtime token access remains necessary for coding processes; hiding the account UI is not a security boundary against arbitrary malicious Bash code.

Browser containers are non-root, read-only, cap-drop ALL, no-new-privileges, no bind/volume mounts or published ports, 768MiB/one CPU, isolated authorization network plus public HTTPS egress. Chromium user-namespace sandbox stays enabled using a reviewed seccomp profile. X11/VNC listen only inside the browser container; backend transports VNC through a fixed `docker exec` relay. Cookies/profile live only in tmpfs. Ownership and resource-role checks gate container operations. Admin logout, cancellation, web shutdown/restart and a maximum 30-minute browser lease clean up temporary authorization resources.

The admin frontend handles official login links using noVNC; it never falls back to opening those links locally when the server browser fails. OAuth URLs and clipboard are memory-only. Clipboard-to-terminal requires a click and the original authorization session/connection; it never adds Enter automatically. The administrator's device accesses only the app's same-origin HTTP/WebSocket traffic for this flow.
